# Database Schema

Mimori uses **Prisma 7.10.1 with PostgreSQL** ([D-003](DECISIONS.md)). The schema lives in [`prisma/schema.prisma`](../prisma/schema.prisma).

| Item | State |
| ---- | ----- |

| Schema | `prisma/schema.prisma` — 8 models, 1 enum, validated |
| Prisma Client | Generated to `generated/prisma` (git-ignored) |
| Migrations | `prisma/migrations/20261101193126_init_global_photo_system`, `prisma/migrations/20261103093000_add_collections`, `prisma/migrations/20261103091753_add_photo_booth_sessions` and `prisma/migrations/20261109120000_add_push_subscriptions` — the first three applied; the push one was verified on a throwaway database and is **not** applied to a real database yet |
| Database | Local PostgreSQL **18.6** database `mimori` on `localhost:5432`, reached through `DATABASE_URL` in a git-ignored `.env`. All three migrations **are applied**: every table, the `PhotoKind` enum, indexes and foreign keys exist. The `Photo` table is the application's **only** image source ([D-033](DECISIONS.md)): the gallery, the eight hero slots, collections, widgets and Recently Added all reference its rows, and no bundled pictures exist. It held no rows after the reset, and now contains only the photos and the one photobooth session created while verifying the save flow (PHOTO-8); they were not deleted. The Neon PostgreSQL database the deployment uses had the first three migrations applied on 2026-11-09 and does **not** yet have the push migration, so `PushSubscription` exists there only after an approved `prisma migrate deploy` |
| Seed data | None |

The database matches the schema exactly: `prisma migrate diff --from-config-datasource --to-schema` reports **"No difference detected"**.

**Images are never stored in PostgreSQL.** Cloudinary holds the files; the database stores the secure URL, the Cloudinary public id and metadata ([D-011](DECISIONS.md)). No binary, `bytea`, Base64 or file-path column exists.

## Global architecture — no ownership model

Mimori has **no `User` model and no `userId` column anywhere** ([D-013](DECISIONS.md)). Every folder, photo, widget and widget selection belongs to the single shared Mimori collection.

There is deliberately no authentication or authorization model: no `User`, `Account`, `Session` or equivalent table exists, and none should be added without a new decision superseding D-013. Adding multi-user ownership later is a schema migration, not a configuration change.

## Models

All ids are `cuid()` strings. Timestamps are UTC and generated by Prisma (`createdAt`, `updatedAt`).

### `Folder`

A folder that groups photos across the whole application. This table is what the **Collections** pages read and write ([D-029](DECISIONS.md)): a collection *is* a folder, not a parallel model.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `name` | `String` | **Globally unique** |
| `description` | `String?` | Optional note shown under the collection name |
| `pinned` | `Boolean` | Default `false`; pinned collections are listed first |
| `coverPhotoId` | `String?` | Gallery `Photo` id used as the cover; `null` falls back to the first photo in the collection |
| `createdAt`, `updatedAt` | `DateTime` | |

**Why `name` is globally unique:** with a single shared collection there is no tenant to scope a duplicate name to, so two folders called "Trips" would be indistinguishable in navigation and in any folder picker. The database rejects the duplicate (`Folder_name_key`) instead of leaving the ambiguity to the UI. The API maps that rejection to a 409 with a readable message; renaming is the escape hatch.

### `CollectionPhoto`

The ordered membership of photos in a collection.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `folderId` | `String` | FK → `Folder`, `ON DELETE CASCADE` |
| `photoId` | `String` | Gallery `Photo` id, in display order. **No foreign key** — see below |
| `position` | `Int` | Display order, default `0`; ties broken by `photoId` |
| `addedAt` | `DateTime` | |

Composite primary key `(folderId, photoId)`: a photo appears at most once per collection, while the same photo can be in many collections. `photoId` holds a gallery `Photo` id and still has **no foreign key**, because a membership is deliberately not an owner of the image ([D-033](DECISIONS.md)). The API validates ids against the `Photo` table on write, and reads filter membership through the same list, so a row whose photo has gone simply leaves the collection instead of rendering broken. Adding a photo never copies or uploads it, and removing a membership row only takes the photo out of that collection. Promoting this column to a real foreign key is a possible later migration; it is not required for correctness.

### `Photo`

The central table for photo metadata. Gallery photos and Photo Booth photos share it.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `folderId` | `String?` | FK → `Folder`, `ON DELETE SET NULL` — **null means unfiled** |
| `kind` | `PhotoKind` | `GALLERY` (default) or `PHOTO_BOOTH` |
| `publicId` | `String` | Cloudinary public id, unique — used for transforms and deletion |
| `secureUrl` | `String` | Cloudinary https delivery URL |
| `caption` | `String?` | |
| `fileName` | `String?` | Original filename, when the upload provides one |
| `width`, `height` | `Int?` | Pixels |
| `mimeType` | `String?` | |
| `fileSize` | `Int?` | Bytes |
| `takenAt` | `DateTime?` | When the photo was taken, not when it was uploaded |
| `createdAt`, `updatedAt` | `DateTime` | Upload/update times |

Optional metadata is nullable rather than defaulted, so "unknown" stays distinguishable from a real value of `0` or `""`.

**Uploads:** `POST /api/photos/upload` is the only writer ([D-030](DECISIONS.md)). It stores one `GALLERY` row per uploaded image and fills `publicId`, `secureUrl`, `fileName`, `mimeType`, `fileSize`, `width` and `height`; the remaining columns stay `NULL` until a UI sets them. `caption` is the photo's title in the gallery viewer, so an uploaded photo with no caption shows no title line. Retrying the same file is deduplicated by `fileName` + `fileSize` + `mimeType` rather than a hash column, and `publicId` stays unique. Deleting a photo through the gallery viewer (`DELETE /api/gallery/[id]`, [D-041](DECISIONS.md)) removes the row, its `CollectionPhoto` rows, any `Folder.coverPhotoId` and its id inside widget and carousel config, then destroys the Cloudinary asset with the row's own `publicId`; no other `Photo` row is touched, and a saved booth's print is refused so its session is never cascaded away ([ISSUE-027](KNOWN_ISSUES.md)).

### `Widget`

A widget that displays a chosen set of photos.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `name` | `String` | |
| `type` | `String` | Widget kind — one of `polaroid`, `photo-grid`, `film-strip`, `heart-collage`, `photo-stack`, `memory-frame`, `love-note`, `our-counter` — or the reserved `hero-carousel` |
| `config` | `Json?` | Widget settings, validated by the application |
| `createdAt`, `updatedAt` | `DateTime` | |

`type` is a plain string rather than an enum so new widget kinds do not need a migration; `config` keeps widget-specific settings out of the relational model. Both are validated in the application layer.

One row is not a Home Page widget: `type = "hero-carousel"` (name "Hero carousel") stores the carousel's eight slots as `{ slots: [{ slotId, photoId, title }] }` ([D-032](DECISIONS.md), [D-033](DECISIONS.md)). `slotId` is one of the fixed `hero-slot-1`…`hero-slot-8`, `photoId` is a gallery `Photo` id and `title` is the text shown under the picture. Only the id is stored — never the URL — so the carousel resolves the current `secureUrl` from the `Photo` row on every read, and a slot whose photo has been deleted reads as empty. A slot with no entry is an empty slot, drawn as a colourful square. The row is hidden from `/api/widgets` because that route only reads catalogue kinds, and it keeps the shared arrangement for every visitor without a new table.

Today `config` carries the whole Home Page layout ([D-025](DECISIONS.md)):

| Key | Type | Notes |
| --- | ---- | ----- |
| `kind` | `string` | Mirrors `type`; checked against the same allowlist |
| `photoIds` | `string[]` | Gallery `Photo` ids, in display order; validated server-side against the photo table |
| `text` | `string` | Love Note copy, a counter label, or a caption override |
| `date` | `string` | `YYYY-MM-DD` start date for Our Counter; `""` when unset |
| `position` | `{ x, y }` | Absolute pixels on the widget canvas, grid-aligned |
| `size` | `"sm" \| "md" \| "lg"` | Size preset |
| `z` | `number` | Painter's order; higher sits in front |

### `WidgetPhoto`

The ordered join between widgets and photos.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `widgetId` | `String` | FK → `Widget`, `ON DELETE CASCADE` |
| `photoId` | `String` | FK → `Photo`, `ON DELETE CASCADE` |
| `position` | `Int` | Display order, default `0`; ties broken by `photoId` |
| `addedAt` | `DateTime` | |

Composite primary key `(widgetId, photoId)`: a photo appears at most once per widget, while the same photo can appear in many widgets. Duplicate associations are therefore impossible.

### `PhotoboothSession`

A saved photobooth print and the editor settings that describe it ([D-037](DECISIONS.md)).

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `photoCount` | `Int` | 2, 3, 4 or 6, validated against the photobooth catalogue |
| `layout` | `String` | `strip` or `collage` |
| `borderKey` | `String` | One of the six border templates in `lib/photo-booth/borders.ts` |
| `backgroundKey` | `String?` | Paper swatch key; `null` keeps the template's own paper |
| `caption` | `String?` | Optional caption, at most 48 characters |
| `showDate` | `Boolean` | Whether the date is printed; default `true` |
| `printDate` | `String?` | The printed date (`YYYY-MM-DD`) — **not** when the row was written |
| `spacing` | `Int` | Gap between photos, in composition units |
| `borderWidth` | `Int` | Frame thickness, in composition units |
| `stickers` | `Json?` | Validated `StickerPlacement[]`: id, sticker key, fractional x/y, size, rotation |
| `printPhotoId` | `String` | FK → `Photo`, `ON DELETE CASCADE`: the finished print |
| `createdAt`, `updatedAt` | `DateTime` | Session history, distinct from `printDate` |

`layout`, `borderKey` and `backgroundKey` are plain strings rather than enums so a new paper or border needs no migration; they are validated in the application layer against the existing catalogues. The settings are columns rather than one JSON blob so Phase 5 can read and validate them field by field.

### `PhotoboothShot`

One captured photograph inside a saved session, in print order.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `sessionId` | `String` | FK → `PhotoboothSession`, `ON DELETE CASCADE` |
| `photoId` | `String` | FK → `Photo`, `ON DELETE CASCADE`; unique, so a capture belongs to one session |
| `position` | `Int` | Capture order from `0`; unique per session |
| `createdAt` | `DateTime` | |

A shot stores only the photo reference — never a URL, size or caption — because the `Photo` row is the single record of the image. The photo's `kind` is `PHOTO_BOOTH`, which is what keeps it out of the Gallery.

Editing a saved session updates the existing `PhotoboothSession` row — every settings column plus `printPhotoId` — and never touches its `PhotoboothShot` rows, so the original captures and their order survive every save. The print it replaced is deleted afterwards only when no other row still refers to it (another session, `CollectionPhoto`, `WidgetPhoto`, a hero-slot `Widget.config` entry or `Folder.coverPhotoId`); otherwise it stays in the Gallery.

## Relationships

There are seven foreign keys in total — no ownership edges remain.

| Relationship | Cardinality | `onDelete` | Reason |
| ------------ | ----------- | ---------- | ------ |
| `Folder` → `Photo` | 1 : N (optional) | `SetNull` | Deleting a folder keeps its photos and moves them to unfiled |
| `Folder` → `CollectionPhoto` | 1 : N | `Cascade` | A deleted collection drops only its membership rows |
| `Widget` → `WidgetPhoto` | 1 : N | `Cascade` | A deleted widget drops its selections |
| `Photo` → `WidgetPhoto` | 1 : N | `Cascade` | A deleted photo disappears from every widget |
| `PhotoboothSession` → `PhotoboothShot` | 1 : N | `Cascade` | A deleted session drops its shot rows, not the photos |
| `Photo` → `PhotoboothShot` | 1 : N | `Cascade` | A deleted capture row goes with its photo |
| `Photo` → `PhotoboothSession` | 1 : N (print) | `Cascade` | A deleted print removes the session that described it |

Deleting a **folder never deletes photos**. This is the behaviour to preserve: `Photo.folderId` is set to `NULL` instead, and the photo stays in the gallery as unfiled. In the Collections UI the equivalent rule is that deleting a collection or removing a photo from it only touches `CollectionPhoto`; the manifest photo is never removed.

Deleting a `Photo` row on its own does not delete its Cloudinary asset: only the gallery's delete path does both, in that order ([D-011](DECISIONS.md), [D-041](DECISIONS.md)). A row removed anywhere else leaves its asset behind, which is why the gallery refuses to delete a row when Cloudinary is not configured and reports a warning when the destroy fails after the row is gone.

### `PushSubscription`

One browser or installed app that agreed to receive Mimori's notifications ([D-061](DECISIONS.md), [PWA-2](FEATURES.md)).

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `endpoint` | `String` | The push service's own URL. **Unique** |
| `p256dh` | `String` | The subscription's public key, used to encrypt a payload to it |
| `auth` | `String` | The subscription's auth secret |
| `expirationTime` | `DateTime?` | `null` when the browser reported no expiry; past rows are pruned before a send |
| `createdAt`, `updatedAt` | `DateTime` | |

There is deliberately **no owner column**: Mimori has no accounts, so a subscription is the device. The unique `endpoint` is what makes registration an upsert — a browser profile or installed app keeps one row, and re-subscribing refreshes its keys instead of adding a second device. The row is written by `POST /api/push/subscribe` and deleted by `DELETE /api/push/subscribe`, or by the server after a delivery the push service answered with `404`/`410`. The private VAPID key is never stored here; it is configuration (`VAPID_PRIVATE_KEY`).

## Distinguishing gallery photos from Photo Booth photos

There is **one** `Photo` table and **one** Cloudinary pipeline. A single `PhotoKind` enum column (`kind`) records the section a photo belongs to:

- `GALLERY` — default, every ordinary photo, including a saved photobooth **print**.
- `PHOTO_BOOTH` — the original captures of a photobooth session, written by its save flow.

Consequences:

- Gallery queries filter `kind = GALLERY`; the Photo Booth section filters `kind = PHOTO_BOOTH`; both use the same model and can share captions, folders and widget selection.
- `Photo_kind_createdAt_idx` makes both filtered listings index-backed.
- A photo is in exactly one section at a time. Moving one between sections is a `kind` update.
- `PhotoboothSession` and `PhotoboothShot` reference `Photo` without a second image store: the print is a `GALLERY` photo and the captures are `PHOTO_BOOTH` photos ([D-037](DECISIONS.md)).

## How a saved photobooth session works

`PhotoboothSession` (settings + print) → `PhotoboothShot` → `Photo`.

- Saving uploads each capture as a `PHOTO_BOOTH` photo and the finished JPEG as a `GALLERY` photo through the same `/api/photos/upload` endpoint, which takes an optional, allowlisted `kind` and stores each kind in its own Cloudinary folder (`mimori/photo-booth`, `mimori/gallery`).
- `POST /api/photo-booth` re-reads the referenced rows, requires every shot to be `PHOTO_BOOTH`, the print to be `GALLERY`, the shot count to equal `photoCount`, and positions to be unique; only then does it create the session with its shots in one nested write.
- Loading a session joins its shots in `position` order and resolves each photo's current `secureUrl`, so nothing in the session duplicates image metadata.
- The print is an ordinary Gallery photo: it appears in `/gallery`, its pickers, collections and the hero slots, while the captures stay invisible because every gallery query filters `kind = GALLERY`.

## How widget-photo relationships work

`Widget` (name, type, JSON config) → `WidgetPhoto` → `Photo`.

- Selecting a photo for a widget inserts a `WidgetPhoto` row with a `position`.
- Loading a widget reads `WidgetPhoto` filtered by `widgetId`, ordered by `position` (then `photoId`), joined to `Photo` for metadata and URLs.
- The same photo can be in any number of widgets, and each widget keeps its own order.
- `config` holds presentation settings (interval, shape, etc.) so new widget types need no schema change.

**Current implementation:** the Home Page widget desktop (WIDGET-1 in [FEATURES.md](FEATURES.md)) does **not** write `WidgetPhoto` rows. Widget photo references live in `config.photoIds`, which now holds gallery `Photo` ids and is validated against the `Photo` table ([D-033](DECISIONS.md)). The join table stays available if widget photos ever move into the relational model.

## How collection membership works

`Folder` (name, description, pinned, cover) → `CollectionPhoto` → gallery `Photo` ids.

- Creating a collection inserts one `Folder` row plus a `CollectionPhoto` row per chosen photo, numbered from `0`.
- Loading a collection reads its rows ordered by `position`, then `photoId`, and resolves them against the `Photo` table; ids whose photo no longer exists are dropped from the response.
- The same photo can be in any number of collections, and each collection keeps its own order.
- Removing a photo deletes only its membership row; deleting a collection cascades to its membership rows. Neither operation touches the `Photo` row or its Cloudinary asset.
- Moving photos between collections is one transaction: rows are deleted from the source and appended to the target, so a failure cannot leave a photo in neither.
- `coverPhotoId` is a gallery `Photo` id and may name any gallery photo, including one that is not a member; `null` falls back to the collection's first photo.

## Conventions

| Topic | Convention |
| ----- | ---------- |
| Model naming | Singular `PascalCase` (`Photo`); Prisma default table names, no `@@map` |
| Field naming | `camelCase`, quoted in raw SQL |
| Primary keys | `String` with `@default(cuid())` |
| Timestamps | `createdAt`, `updatedAt` on every model; `updatedAt` enforced by `@updatedAt` |
| Deletion | Hard deletes; folder deletion un-files photos, widget and photo deletion cascade to `WidgetPhoto` |
| Ownership | None — every model is global ([D-013](DECISIONS.md)) |
| Enums | `PascalCase` names, `SCREAMING_SNAKE_CASE` values (`PhotoKind`, `GALLERY`) |
| Nullability | Optional metadata nullable, never a sentinel default |
| Migrations | `prisma migrate`, checked in under `prisma/migrations`; never `db push` in place of a migration |
| Money/precision | Not applicable yet |

## Media and storage

Media lives in Cloudinary; PostgreSQL stores references and metadata ([D-011](DECISIONS.md)).

- `Photo.secureUrl` is the delivery URL; `Photo.publicId` is the handle for transforms and deletion.
- Upload is implemented through `POST /api/photos/upload`; a failed row write destroys the asset it just uploaded. There is no user-facing delete or transform flow, so deleting a `Photo` row still leaves its Cloudinary asset.
- Nothing in the schema stores, encodes or streams image bytes.

## Known limitations of this schema

| Limitation | Impact | Handling |
| ---------- | ------ | -------- || No production database | Only the local development database exists | Provision one and run `npx prisma migrate deploy` before deploying |
| Prisma 7 needs a driver adapter at runtime | `new PrismaClient()` requires an adapter such as `@prisma/adapter-pg`; neither it nor `pg` is installed | Add the adapter with the first data-access code |
| No ownership or access control | Anyone who can reach the app sees the whole collection | Intentional ([D-013](DECISIONS.md)); if Mimori ever has more than its two intended users, access control is a new decision |
| Widget types are free-form strings | Typos are not caught by the compiler | Validated against the eight-kind allowlist in `lib/widgets/validate.ts` and re-checked on read in `lib/widgets/server.ts` |
| `position` is not unique per widget | Two rows in one widget may share a position; order falls back to `photoId` | Reorder logic should rewrite positions; a unique `(widgetId, position)` can be added if ties become a problem |
| Deleting a photo leaves its Cloudinary asset | Orphaned assets and storage cost | Delete the Cloudinary asset in the same operation, once the media layer exists |
| `Photo.kind` is fixed at one section per photo | A photo cannot be shown in both Gallery and Photo Booth simultaneously | Accepted for now; a join table would be needed if that changes |
| `CollectionPhoto.photoId` is not a foreign key | A membership can reference an id whose photo no longer exists | Reads filter against the `Photo` table, so a stale id is dropped from the response rather than rendered as a broken image; promoting it to a real FK is a possible later migration ([D-033](DECISIONS.md)) |

## Maintenance rules

- Add a model section here in the same change that adds it to `schema.prisma`.
- Document relationships, constraints, indexes and the reason a model exists — not just its fields.
- Record every migration-worthy change in [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md).
- Never document a model that does not exist in code.
- Never introduce a column that stores image bytes, Base64 content or file paths.
