# Database Schema

Mimori uses **Prisma 7.10.1 with PostgreSQL** ([D-003](DECISIONS.md)). The schema lives in [`prisma/schema.prisma`](../prisma/schema.prisma).

## Current state

| Item | State |
| ---- | ----- |
| Prisma CLI and Client | Installed, pinned at `7.10.1` (`package.json`) |
| Schema | `prisma/schema.prisma` — 4 models, 1 enum, validated |
| Prisma Client | Generated to `generated/prisma` (git-ignored) |
| Migrations | `prisma/migrations/20261101193126_init_global_photo_system` — applied |
| Database | Local PostgreSQL **18.6** database `mimori` on `localhost:5432`, reached through `DATABASE_URL` in a git-ignored `.env`. The migration **is applied**: the four tables, `PhotoKind` enum, indexes and foreign keys exist and contain no application data. No production database exists |
| Seed data | None |

The database matches the schema exactly: `prisma migrate diff --from-config-datasource --to-schema` reports **"No difference detected"**.

**Images are never stored in PostgreSQL.** Cloudinary holds the files; the database stores the secure URL, the Cloudinary public id and metadata ([D-011](DECISIONS.md)). No binary, `bytea`, Base64 or file-path column exists.

## Global architecture — no ownership model

Mimori has **no `User` model and no `userId` column anywhere** ([D-013](DECISIONS.md)). Every folder, photo, widget and widget selection belongs to the single shared Mimori collection.

There is deliberately no authentication or authorization model: no `User`, `Account`, `Session` or equivalent table exists, and none should be added without a new decision superseding D-013. Adding multi-user ownership later is a schema migration, not a configuration change.

## Models

All ids are `cuid()` strings. Timestamps are UTC and generated by Prisma (`createdAt`, `updatedAt`).

### `Folder`

A folder that groups photos across the whole application.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `name` | `String` | **Globally unique** |
| `description` | `String?` | |
| `createdAt`, `updatedAt` | `DateTime` | |

**Why `name` is globally unique:** with a single shared collection there is no tenant to scope a duplicate name to, so two folders called "Trips" would be indistinguishable in navigation and in any folder picker. The database rejects the duplicate (`Folder_name_key`) instead of leaving the ambiguity to the UI. Renaming is the escape hatch.

### `Photo`

The central table for photo metadata. Gallery photos and Photo Booth photos share it.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `folderId` | `String?` | FK → `Folder`, `ON DELETE SET NULL` — **null means unfiled** |
| `kind` | `PhotoKind` | `GALLERY` (default) or `PHOTO_BOOTH` |
| `publicId` | `String` | Cloudinary public id, unique — used for transforms and deletion |
| `secureUrl` | `String` | Cloudinary https delivery URL |
| `caption` | `String?` | |
| `fileName` | `String?` | Original filename, when the upload provides one |
| `width`, `height` | `Int?` | Pixels |
| `mimeType` | `String?` | |
| `fileSize` | `Int?` | Bytes |
| `takenAt` | `DateTime?` | When the photo was taken, not when it was uploaded |
| `createdAt`, `updatedAt` | `DateTime` | Upload/update times |

Optional metadata is nullable rather than defaulted, so "unknown" stays distinguishable from a real value of `0` or `""`.

### `Widget`

A widget that displays a chosen set of photos.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `id` | `String` | Primary key |
| `name` | `String` | |
| `type` | `String` | Widget kind — one of `polaroid`, `photo-grid`, `film-strip`, `heart-collage`, `photo-stack`, `memory-frame`, `love-note`, `our-counter` |
| `config` | `Json?` | Widget settings, validated by the application |
| `createdAt`, `updatedAt` | `DateTime` | |

`type` is a plain string rather than an enum so new widget kinds do not need a migration; `config` keeps widget-specific settings out of the relational model. Both are validated in the application layer.

Today `config` carries the whole Home Page layout ([D-025](DECISIONS.md)):

| Key | Type | Notes |
| --- | ---- | ----- |
| `kind` | `string` | Mirrors `type`; checked against the same allowlist |
| `photoIds` | `string[]` | Gallery manifest ids (`lib/photos.ts`), in display order; validated server-side |
| `text` | `string` | Love Note copy, a counter label, or a caption override |
| `date` | `string` | `YYYY-MM-DD` start date for Our Counter; `""` when unset |
| `position` | `{ x, y }` | Absolute pixels on the widget canvas, grid-aligned |
| `size` | `"sm" \| "md" \| "lg"` | Size preset |
| `z` | `number` | Painter's order; higher sits in front |

### `WidgetPhoto`

The ordered join between widgets and photos.

| Field | Type | Notes |
| ----- | ---- | ----- |
| `widgetId` | `String` | FK → `Widget`, `ON DELETE CASCADE` |
| `photoId` | `String` | FK → `Photo`, `ON DELETE CASCADE` |
| `position` | `Int` | Display order, default `0`; ties broken by `photoId` |
| `addedAt` | `DateTime` | |

Composite primary key `(widgetId, photoId)`: a photo appears at most once per widget, while the same photo can appear in many widgets. Duplicate associations are therefore impossible.

## Relationships

There are three foreign keys in total — no ownership edges remain.

| Relationship | Cardinality | `onDelete` | Reason |
| ------------ | ----------- | ---------- | ------ |
| `Folder` → `Photo` | 1 : N (optional) | `SetNull` | Deleting a folder keeps its photos and moves them to unfiled |
| `Widget` → `WidgetPhoto` | 1 : N | `Cascade` | A deleted widget drops its selections |
| `Photo` → `WidgetPhoto` | 1 : N | `Cascade` | A deleted photo disappears from every widget |

Deleting a **folder never deletes photos**. This is the behaviour to preserve: `Photo.folderId` is set to `NULL` instead, and the photo stays in the gallery as unfiled.

Deleting rows does not delete Cloudinary assets: removing a `Photo` only removes its metadata, and the asset must be deleted through the Cloudinary API by the application ([D-011](DECISIONS.md)).

## Unique constraints and indexes

| Constraint | Type | Serves |
| ---------- | ---- | ------ |
| `Folder_pkey` | PK | `id` |
| `Folder_name_key` | unique | Folder names are globally unique; duplicate names rejected |
| `Photo_pkey` | PK | `id` |
| `Photo_publicId_key` | unique | Cloudinary asset lookup, prevents duplicate imports |
| `Photo_kind_createdAt_idx` | index | Gallery listing and the Photo Booth section: filter by `kind`, newest first |
| `Photo_folderId_createdAt_idx` | index | Photos inside one folder, newest first |
| `Photo_createdAt_idx` | index | Unfiltered "all photos, newest first" |
| `Widget_pkey` | PK | `id` |
| `Widget_type_idx` | index | Listing widgets by type |
| `WidgetPhoto_pkey` | PK `(widgetId, photoId)` | Prevents duplicate widget↔photo pairs |
| `WidgetPhoto_widgetId_position_idx` | index | Loading a widget's photos in display order |
| `WidgetPhoto_photoId_idx` | index | "Which widgets use this photo?" and cascade deletes |

## Distinguishing gallery photos from Photo Booth photos

There is **one** `Photo` table and **one** Cloudinary pipeline. A single `PhotoKind` enum column (`kind`) records the section a photo belongs to:

- `GALLERY` — default, every ordinary photo.
- `PHOTO_BOOTH` — photos captured or uploaded through the Photo Booth section.

Consequences:

- Gallery queries filter `kind = GALLERY`; the Photo Booth section filters `kind = PHOTO_BOOTH`; both use the same model and can share captions, folders and widget selection.
- `Photo_kind_createdAt_idx` makes both filtered listings index-backed.
- A photo is in exactly one section at a time. Moving one between sections is a `kind` update.
- New Photo Booth capabilities (sessions, stickers, frames) can add tables that reference `Photo` later without a second image store.

## How widget-photo relationships work

`Widget` (name, type, JSON config) → `WidgetPhoto` → `Photo`.

- Selecting a photo for a widget inserts a `WidgetPhoto` row with a `position`.
- Loading a widget reads `WidgetPhoto` filtered by `widgetId`, ordered by `position` (then `photoId`), joined to `Photo` for metadata and URLs.
- The same photo can be in any number of widgets, and each widget keeps its own order.
- `config` holds presentation settings (interval, shape, etc.) so new widget types need no schema change.

**Current implementation:** the Home Page widget desktop (WIDGET-1 in [FEATURES.md](FEATURES.md)) does **not** write `WidgetPhoto` rows yet, because the gallery is a local manifest rather than `Photo` rows ([D-015](DECISIONS.md)). Widget photo references live in `config.photoIds` and are validated against that manifest ([D-025](DECISIONS.md)). The join table stays available for the point at which photos are stored in `Photo`.

## Conventions

| Topic | Convention |
| ----- | ---------- |
| Model naming | Singular `PascalCase` (`Photo`); Prisma default table names, no `@@map` |
| Field naming | `camelCase`, quoted in raw SQL |
| Primary keys | `String` with `@default(cuid())` |
| Timestamps | `createdAt`, `updatedAt` on every model; `updatedAt` enforced by `@updatedAt` |
| Deletion | Hard deletes; folder deletion un-files photos, widget and photo deletion cascade to `WidgetPhoto` |
| Ownership | None — every model is global ([D-013](DECISIONS.md)) |
| Enums | `PascalCase` names, `SCREAMING_SNAKE_CASE` values (`PhotoKind`, `GALLERY`) |
| Nullability | Optional metadata nullable, never a sentinel default |
| Migrations | `prisma migrate`, checked in under `prisma/migrations`; never `db push` in place of a migration |
| Money/precision | Not applicable yet |

## Media and storage

Media lives in Cloudinary; PostgreSQL stores references and metadata ([D-011](DECISIONS.md)).

- `Photo.secureUrl` is the delivery URL; `Photo.publicId` is the handle for transforms and deletion.
- Upload, transformation and deletion flows are **not implemented** — schema only.
- Nothing in the schema stores, encodes or streams image bytes.

## Known limitations of this schema

| Limitation | Impact | Handling |
| ---------- | ------ | -------- || No production database | Only the local development database exists | Provision one and run `npx prisma migrate deploy` before deploying |
| Prisma 7 needs a driver adapter at runtime | `new PrismaClient()` requires an adapter such as `@prisma/adapter-pg`; neither it nor `pg` is installed | Add the adapter with the first data-access code |
| No ownership or access control | Anyone who can reach the app sees the whole collection | Intentional ([D-013](DECISIONS.md)); if Mimori ever has more than its two intended users, access control is a new decision |
| Widget types are free-form strings | Typos are not caught by the compiler | Validated against the eight-kind allowlist in `lib/widgets/validate.ts` and re-checked on read in `lib/widgets/server.ts` |
| `position` is not unique per widget | Two rows in one widget may share a position; order falls back to `photoId` | Reorder logic should rewrite positions; a unique `(widgetId, position)` can be added if ties become a problem |
| Deleting a photo leaves its Cloudinary asset | Orphaned assets and storage cost | Delete the Cloudinary asset in the same operation, once the media layer exists |
| `Photo.kind` is fixed at one section per photo | A photo cannot be shown in both Gallery and Photo Booth simultaneously | Accepted for now; a join table would be needed if that changes |

## Maintenance rules

- Add a model section here in the same change that adds it to `schema.prisma`.
- Document relationships, constraints, indexes and the reason a model exists — not just its fields.
- Record every migration-worthy change in [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md).
- Never document a model that does not exist in code.
- Never introduce a column that stores image bytes, Base64 content or file paths.
