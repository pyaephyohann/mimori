# Decisions

Accepted technical and product decisions for Mimori, with the reasoning behind them. A decision here is binding until it is superseded by a later entry.

## Status values

- **Accepted** — in effect.
- **Superseded** — replaced by a newer decision.
- **Proposed** — suggested, not yet agreed. Not binding.

---

## D-001 — Project name: Mimori

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** The project is named **Mimori**.
- **Context:** The product needed a stable identity before documentation, repository metadata and design work.
- **Consequences:** Package name, page metadata and all documentation use "Mimori". The name is used consistently for the application, its documentation and its user-facing identity.

---

## D-002 — Framework and language: Next.js with TypeScript

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** Mimori is built with **Next.js** and **TypeScript**.
- **Context:** A single framework that supports both server-rendered pages and an installable PWA delivery model, with static typing for a long-lived personal project.
- **Consequences:** All application code is TypeScript. Framework conventions and the version installed in the repository take precedence over general Next.js knowledge. Adding another framework or a plain-JavaScript area requires a new decision.

---

## D-003 — Data layer: Prisma with PostgreSQL

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** Persistence uses **Prisma** as the ORM over **PostgreSQL**.
- **Context:** A relational store suits the structured, related nature of memories, dates and anniversaries; Prisma provides a typed schema and a migration workflow.
- **Consequences:** The data model lives in a Prisma schema and is documented in [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md). Prisma is now integrated — schema, migration and generated client — while PostgreSQL is still **not provisioned** (see [TECH_STACK.md](TECH_STACK.md) and [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)). No alternative database or ORM may be introduced without a new decision.

---

## D-004 — Application type: PWA-first web application

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** Mimori is a **PWA-first web application**. The installable, app-like experience is the primary target rather than a later enhancement.
- **Context:** The product should be kept on a home screen and opened like an app, while still being delivered over the web.
- **Consequences:** Installability is treated as a first-class requirement ([R-1](PRODUCT_REQUIREMENTS.md)). New work must not compromise it. The application must still work as an ordinary website ([R-3](PRODUCT_REQUIREMENTS.md)). Advanced PWA capabilities — offline support, push notifications, background sync — are **not** implied by this decision and remain unconfirmed.

## D-005 — Design direction: mobile-first, responsive

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** Design is **mobile-first**, with responsive support for tablet and desktop.
- **Context:** A personal, frequently-opened keepsake is mostly used on a phone; the app-like experience is strongest on small touch screens.
- **Consequences:** Layouts, interaction and performance are designed for small screens first and adapted upward. Desktop is fully supported but is not the baseline that drives layout decisions.

## D-006 — Documentation system in `docs/`

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** The project maintains a documentation system at the repository root (`AGENTS.md`, `knowledge.md`) and in `docs/`, updated as part of the work that changes what it describes.
- **Context:** Both humans and AI agents work on Mimori; a shared, accurate record of intent, status and constraints prevents drift and duplicated effort.
- **Consequences:** Documents are part of the definition of done. Any change that alters architecture, schema, features or scope updates the relevant document in the same task. Documentation must describe reality — undecided items are marked `TBD`.

## D-007 — Typography: Roboto body, Caveat decorative

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** **Roboto** is the application's default font. **Caveat** is the decorative script font, used only for romantic headings, handwritten-style labels and similar short accents.
- **Context:** The product needs a neutral, highly legible body face plus one expressive face that carries the cozy tone without hurting readability.
- **Consequences:** Both fonts are self-hosted through `next/font/google` in the root layout and exposed as tokens (`--font-body`, `--font-script`) plus the Tailwind utilities `font-sans` and `font-decorative`. Caveat is opt-in only — never for paragraphs, forms or long copy. Changing either font means updating the two `next/font` calls in `app/layout.tsx` and the two token mappings in `app/globals.css`; no new dependency is involved.

## D-008 — Colour system: fixed brand palette, semantic roles, native theme

- **Status:** Accepted — its page-background choice is superseded by [D-010](#d-010--page-background-hot-pink-in-both-themes); everything else stands.
- **Date:** 2026-11-01
- **Decision:** The eight brand colours are fixed `--brand-*` tokens whose HEX values are identical in every theme. Components consume only semantic role tokens (`--background`, `--surface`, `--surface-muted`, `--border`, `--heading`, `--foreground`, `--muted-foreground`, `--primary*`, `--accent*`, `--ring`), which are re-mapped per theme. Five status families (`success`, `warning`, `danger`, `info`, `neutral`) each carry a foreground, surface and border token and are kept separate from the brand palette. Theme follows the operating system via `prefers-color-scheme`; no theme-switching interface exists.
- **Context:** A single source of truth prevents per-component colour logic, keeps the supplied brand values exact, and lets the app respond to light/dark preference on day one.
- **Consequences:** New colours are added as tokens in `app/globals.css`, never hardcoded in components. A manual switcher can later override the same semantic variables (for example `[data-theme="dark"]`) without touching component code. Contrast limits that follow from the fixed brand values are recorded in [KNOWN_ISSUES.md](KNOWN_ISSUES.md).

## D-009 — Primary buttons keep white text on Candy Pink

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** Primary buttons use **Candy Pink `#FF4FA3`** as the background, **Deep Candy Pink `#F02E8D`** on hover, and **white `#FFFFFF`** for the label. All three values are fixed; the white label is a deliberate choice and not an oversight.
- **Context:** The design-system audit measured white on Candy Pink at **3.04:1** and white on Deep Candy Pink at **3.83:1** — below WCAG AA (1.4.3) for normal-size text. The palette was reviewed and the brand look was chosen over altering either the button background or the label colour.
- **Consequences:** `--primary`, `--primary-hover`, `--primary-foreground` and the `--brand-candy-pink` / `--brand-deep-candy-pink` / `--brand-white` values must not be changed to improve contrast without a new decision superseding this one. Normal-size white labels do **not** meet WCAG AA (4.5:1); AA-large (≥18.66px bold or ≥24px) is met, so primary button labels should be rendered at large-text sizes wherever the layout allows. Tracked as [ISSUE-002](KNOWN_ISSUES.md).

## D-010 — Page background: Hot Pink in both themes

- **Status:** Accepted
- **Date:** 2026-11-01
- **Decision:** The page background is **Hot Pink `#FF69B4`** in **both** the light and dark themes, through the `--brand-hot-pink` token referenced by `--background`. This supersedes the page-background part of [D-008](#d-008--colour-system-fixed-brand-palette-semantic-roles-native-theme), which used Rose Pink in light and `#1B1216` in dark.
- **Context:** Approved product change: the app should sit on one hot pink canvas regardless of theme, rather than a pink light surface and a near-black dark surface.
- **Consequences:** Update 2026-11-02: Mimori is now light mode only ([D-028](#d-028--light-mode-only)), so the dark-theme half of the comparison below is historical. All other brand values, the primary button (D-009), Soft White and dark surfaces, typography and the status palettes are unchanged; `--brand-rose-pink` `#E88EAD` remains a palette value but is no longer the page background. Because the canvas is now a light, saturated pink in both themes, text tokens tuned for the old canvases fall below WCAG AA on it: light body text **4.31:1** (was 4.83:1) and light muted **2.45:1**, while dark-theme near-white text drops to **2.31:1** (was 16.02:1) with heading 2.53:1 and muted 1.34:1. **No compensating colour change was made** — re-tuning any text token requires a new decision. Tracked as [ISSUE-001](KNOWN_ISSUES.md), [ISSUE-004](KNOWN_ISSUES.md) and [ISSUE-005](KNOWN_ISSUES.md).

## D-011 — Media storage: Cloudinary, references only in PostgreSQL

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** Images are stored and served by **Cloudinary**. PostgreSQL stores only the Cloudinary `secureUrl`, the `publicId` and image metadata (`fileName`, `width`, `height`, `mimeType`, `fileSize`, `takenAt`). No image bytes, binary columns, Base64 content or local file paths are ever written to the database.
- **Context:** Photos are the core content of the product, and a relational database is the wrong place for image payloads — it bloats backups, bypasses image transformation and CDN delivery, and makes the app slow to read.
- **Consequences:** `Photo.publicId` is unique and is the handle for transforms and deletion. Deleting a `Photo` row does **not** delete the Cloudinary asset; the media layer must delete the asset in the same operation. The upload, transform and deletion flows were not implemented when this decision was made; **update 2026-11-03:** uploads are now implemented ([D-030](#d-030--the-gallery-is-database-first-with-the-bundled-photos-as-its-fallback-and-uploads-are-server-signed)), while transforms and asset deletion remain unimplemented. Cloudinary is used through the server only; credentials must never reach the client ([SECURITY.md](SECURITY.md)).

## D-012 — Photo management data model

- **Status:** Accepted — its ownership part is superseded by [D-013](#d-013--global-data-model-no-user-ownership); the rest stands.
- **Date:** 2026-11-02
- **Decision:** Photos live in **one** central `Photo` table, distinguished by a `PhotoKind` enum (`GALLERY` | `PHOTO_BOOTH`). Folders group photos (`Photo.folderId` nullable, `ON DELETE SET NULL`). Widgets select photos through an ordered join table `WidgetPhoto` with a `position`, and keep widget-specific settings in a `Json` `config` column.
- **Context:** Photo Booth is a separate product section but not a separate kind of image, so duplicating storage would double the upload, deletion and metadata code. Widgets need both a chosen set of photos and an order, which a many-to-many column or JSON array cannot express safely.
- **Consequences:** Gallery and Photo Booth are filtered views over the same model (`kind`), and both are index-backed. Deleting a folder keeps its photos and un-files them; deleting a photo drops its widget links. `Widget.type` is a free-form string and `config` a JSON object so new widget kinds need no migration — both must be validated in the application. The original `User` owner and `userId` columns were removed by [D-013](#d-013--global-data-model-no-user-ownership). Full detail in [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md).

## D-013 — Global data model: no user ownership

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** Mimori's database is **global**. There is no `User` model, no `userId` column and no per-user ownership or authorization relationship. `Folder`, `Photo`, `Widget` and `WidgetPhoto` belong to the single shared Mimori collection. `Folder.name` is **globally unique**. No authentication or authorization model is introduced.
- **Context:** Mimori is a private keepsake for one couple, not a multi-tenant product. A `User` row would have existed only to hold an id nothing yet authenticated against, while forcing every query to carry a `userId` filter that no code enforced. Recreating the database before the first migration made the simplification cheap.
- **Consequences:** Queries drop the ownership scope entirely; there is no "cross-user access" class of bug because there is no second user. Anyone who can reach the deployed app sees the whole collection, so deployment must not expose it publicly without a new access-control decision. Folder names can no longer repeat, so "Trips" and "Trips" are rejected by `Folder_name_key`. Re-introducing multi-user support later is a schema migration plus an authorization layer, not a configuration change. The database was deliberately dropped and recreated empty before this model was written; no data was lost because none existed.

## D-014 — Homepage direction: Romantic Scrapbook

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The `/` homepage is a **Romantic Scrapbook**: polaroid-style frames with soft paper surfaces, subtle rotations, handwritten Caveat captions, small 🎀 bow stickers, hand-drawn hearts/arrows/spirals and light floating decoration. Polaroid frames are built on `--surface`, so captions sit on a readable surface in each theme. No UI framework or dependency was added; `app/globals.css` gained only four scrapbook primitives (tilt, hover lift, two float animations) plus their reduced-motion overrides.

## D-015 — Homepage photo source: local manifest, not the database

- **Status:** Superseded by [D-033](#d-033--the-gallery-database-is-the-only-image-source-and-the-carousel-has-eight-fixed-slots); the manifest no longer exists. Left for history.
- **Date:** 2026-11-02
- **Decision:** The homepage reads its photos from `lib/photos.ts`, a typed manifest of JPEG files in `public/couple-images`. Neither Prisma nor Cloudinary is involved yet.
- **Context:** No data-access layer or query exists, `@prisma/adapter-pg` is not installed, and no Cloudinary assets exist ([D-011](#d-011--media-storage-cloudinary-references-only-in-postgresql)). The user supplied real photos to display now, and fabricating images was explicitly ruled out.
- **Consequences:** Adding or removing a photo means adding the file and a manifest entry — the two can drift, and nothing validates that a path exists at runtime. Captions and alt text live only in that manifest, which is the single place to edit them. `Photo`/Cloudinary remain the eventual sources (`PHOTO-1`, `MEDIA-1` in [FEATURES.md](FEATURES.md)).

## D-016 — HEIC originals get JPEG derivatives

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** Every `.HEIC` photo in `public/couple-images` has a JPEG sibling (longest edge 1600px, quality 82) generated with macOS `sips`. The UI references the JPEGs only; the `.HEIC` originals are kept and left untouched.
- **Context:** Seven of the eight supplied photos were `.HEIC`, which browsers cannot decode, so they would render as broken images.
- **Consequences:** The derivatives are the web assets and are what `next/image` optimizes. The originals remain in `public/` and are still served statically if requested, adding roughly 12 MB of unusable payload to the folder — tracked as [ISSUE-007](KNOWN_ISSUES.md). Any future iPhone import needs the same conversion step until the upload pipeline handles it.

## D-017 — Visit randomization contract for hero and gallery

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The hero carousel and the gallery each shuffle on every visit, **independently**. The previous visit's order is stored in `localStorage` under `mimori:hero-order` and `mimori:gallery-order`. A new order never repeats the previous arrangement, and with three or more photos never opens on the previous first photo. Shuffling runs once per mount, after hydration, so server and client markup match and re-renders never reshuffle.
- **Context:** The approved brief asked for per-visit randomization that must not fight React, must survive photo additions/removals, and must not repeat the previous visit's sequence.
- **Consequences:** The rules are pure functions in `lib/randomize.ts`, covered by `lib/randomize.test.ts` on Node's built-in test runner, so no test dependency was added. A single photo keeps its only arrangement; storage failure (private mode) degrades to a plain random order. Because both sections draw from the same eight photos ([D-015](#d-015--homepage-photo-source-local-manifest-not-the-database)), the same photo can appear in both — tracked as [ISSUE-008](KNOWN_ISSUES.md).

## D-018 — Polaroid paper stays white in both themes

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** Scrapbook cards use a dedicated `--paper` surface, `--paper-foreground` text and `--paper-edge` border that are **the same in light and dark themes**: Soft White `#FFF8FA` paper, Warm Charcoal `#49343D` captions, Blush Pink `#F9E1EA` image placeholder. Polaroids and the empty-state cards use `bg-paper`, `text-paper-foreground` and `ring-paper-edge` instead of `--surface`.
- **Context:** The frames were built on `--surface`, which is Soft White in light mode but `#2A1F24` in dark mode, so the polaroids turned black and no longer matched the approved white-paper reference.
- **Consequences:** Photos sit on white paper regardless of theme, as in the reference. Captions keep a **10.89:1** contrast because the text token moved with the card rather than following `--foreground`. The tokens are theme-independent, so they are defined once in `:root` and not overridden in the dark block; `--surface` remains the themed surface for future neutral panels. This supersedes the "polaroid frames are built on `--surface`" consequence of [D-014](#d-014--homepage-direction-romantic-scrapbook) only.

## D-019 — framer-motion and the hero running border

- **Status:** Accepted — its placement and gradient are superseded by [D-020](#d-020--the-running-border-wraps-the-hero-carousel-container); the dependency and the rotation technique stand.
- **Date:** 2026-11-02
- **Decision:** `framer-motion` `14.9.0` is the project's **only** animation library, added for one feature: an animated running border on the hero. The border is built from two layers masked to their own padding band — a 3px core ring and a wide, dim band — each containing one oversized conic-gradient layer rotating a single infinite revolution every 6 seconds, plus a soft pink `box-shadow` bloom outside the framed element. Under `prefers-reduced-motion` the rotation stops and the rings remain as a static border.
- **Context:** The brief asked for a soft stream of pink light travelling around the hero, following the container's rounded shape rather than reading as a separate rectangle. No animation library was installed and no other was permitted.
- **Consequences:** Animation runs as a transform on two composited layers, so it never re-renders React and framer-motion stops it on unmount. `mask-composite` is what makes the effect read as a border; without it the rings are dropped by an `@supports` guard rather than painting over the photos. The rings sit inside the frame with `pointer-events: none`, so carousel navigation and image interaction are unaffected.

## D-020 — The running border wraps the hero carousel container

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The animated running border surrounds the **whole hero carousel container**, not individual photos or polaroid frames. The container is a single rounded frame — `max-w-5xl`, `--carousel-radius` `28px`, `overflow-hidden`, a **static pure white edge** (`border-[var(--brand-white)]`, 2px on mobile and 3px from `sm` up), `p-3` on mobile and `p-5` from `sm` up, and a soft white halo through `--carousel-glow` — with both rings inset `0` inside it, just within the white edge. The running gradient is built **only from the page's own Hot Pink** (`--run-pink: var(--brand-hot-pink)`, `#FF69B4`): the stops are that colour and tints of it mixed toward white with `color-mix()`, ordered so the first and last stops match and the loop has no visible seam. The rotation is slow (one revolution every 9 seconds) so it drifts rather than spins. Polaroid frames keep their existing design and carry no border, animation or glow of their own.
- **Context:** The first implementation lit only the active polaroid, so the border read as an effect on a photo rather than on the carousel. The corrected requirement is one continuous border around the carousel's outer container.
- **Consequences:** The gradient lives in `app/globals.css` beside the other tokens and the rings read it from there, so `RunningBorder` takes no styling props. No new pink enters the project: every stop derives from `--brand-hot-pink`, and the palette in [D-008](#d-008--colour-system-fixed-brand-palette-semantic-roles-native-theme) is untouched. Where `color-mix()` is unavailable the gradient falls back to the solid `--run-pink`, so the border still paints. The white static edge is what separates the frame from the Hot Pink canvas, which closes [ISSUE-009](KNOWN_ISSUES.md). The frame is wider (`max-w-5xl` against the page's `max-w-6xl`) and the slides grew with it — `86cqi`, then `26rem` and `30rem` at the `sm` and `lg` breakpoints — so the featured polaroid scales up without distortion. Because the frame clips its contents, the peeking neighbouring polaroids run off the frame's rounded edge instead of crossing the border; the track still scrolls natively and the dots, arrows and arrow keys are unaffected. Gallery cards keep `--polaroid-radius` `4px` and remain unanimated, so the effect is confined to the hero.

## D-021 — The favicon is a vector bow from the brand palette

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The favicon is the homepage's pink bow. The homepage bow is the 🎀 emoji rendered by the system font (`BowSticker` in `components/scrapbook/doodles.tsx`), not an image, so the icon is a **hand-drawn vector of that bow** — two loops, a knot and two ribbon tails — in brand values only: Candy Pink `#FF4FA3` loops, Deep Candy Pink `#F02E8D` knot and tails, a Soft White `#FFF8FA` highlight. It ships through Next's metadata file conventions as `app/icon.svg` (scalable, `sizes="any"`), `app/favicon.ico` (16/32/48 PNG-in-ICO) and `app/apple-icon.png` (180×180, bow on Soft White). No `metadata.icons` entry and no `layout.tsx` change is made: the files themselves produce the `<link>` tags.
- **Context:** The brief asked the favicon to reuse the existing homepage bow rather than introduce a new logo. An emoji glyph cannot be redistributed as an asset or scaled as vectors, and rendering the emoji itself would depend on the viewer's platform font.
- **Consequences:** The vector is an approximation of the emoji's shape, not the glyph itself; if the homepage bow is ever replaced by a real SVG, the favicon should be regenerated from that file so the two stay identical. The PNG and ICO rasters are derived from `icon.svg` (rasterised at high density and downscaled, so the 16px icon keeps clean edges) and are committed as binaries; regenerating them currently means re-running that rasterisation rather than a repo script. `apple-icon.png` is opaque because iOS fills transparent corners with black, while `icon.svg` and the ICO keep a transparent background. The bow is centred to within half a pixel at 16, 32 and 48px.

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The site navigation is one component (`components/nav/site-nav.tsx`) rendered by the root layout: a white paper bar with the bow mark and "Mimori", five destinations, and an Add Memory action. Home links to `/` and Gallery to its own route, `/gallery` (originally the homepage section's `/#gallery` anchor, moved in [D-027](#d-027--the-gallery-is-its-own-page-and-its-photo-viewer-uses-the-manifest-caption-as-the-title)). The desktop bar appears from `lg`; below that, a compact top bar plus a fixed bottom bar carry the same destinations.

Adding a route later is a one-line change in the `DESTINATIONS` array — the link appears and the entry stops being disabled automatically. The stacked breakpoint was chosen over `md` so the five labels never overflow the bar on tablets. The active pill uses Deep Candy Pink on Blush Pink at **3.10:1**, below WCAG AA for normal text; the palette is fixed ([D-008](#d-008--colour-system-fixed-brand-palette-semantic-roles-native-theme)) so no compensating colour was invented.

Both desktop and mobile bars update their labels when navigating. Future route additions will automatically enable the corresponding entries and button actions.

## D-024 — Clickable cursor is an explicit `cursor-pointer` utility per control

- **Status:** Accepted — supersedes the single base-layer selector tried first.
- **Date:** 2026-11-02
- **Decision:** Each clickable control adds Tailwind's `cursor-pointer` to its own `className`: the brand link, the desktop and the mobile destination links, the mobile menu toggle, both carousel arrows (through the shared `arrowButton` constant) and every carousel dot. There is **no global cursor rule** in `app/globals.css`. Disabled and unavailable controls keep their own cursor instead — `disabled:cursor-not-allowed` on the Add button and the arrows, `cursor-default` on the `aria-disabled` Collections and Photo Booth entries.
- **Context:** The first implementation put one `:is(...)` selector in the base layer, which covered every control at once. The project's convention is that component styling lives beside the component, so the choice was revised in favour of explicit utilities.
- **Consequences:** The cursor is visible next to the markup it affects, and no global selector has to be reasoned about when reading a component or when overriding a cursor. The cost is that a new control must add the class itself — nothing supplies it automatically, and Tailwind 4.3.3's preflight gives `<button>` no pointer cursor — while a disabled control needs the matching disabled cursor instead. Non-interactive surfaces (polaroid frames, gallery photos, decorative stickers, page text, the carousel's scroll container and the mobile bar's tap-to-dismiss wrapper) deliberately carry no cursor class and are not made clickable by this convention.

## D-025 — Widget arrangement is stored in `Widget.config`; no migration was needed

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** The Home Page widget desktop persists through the existing global `Widget` table with **no schema change and no migration**. `Widget.type` holds one of the eight catalogue kinds, `Widget.name` the catalogue title, and `Widget.config` a JSON object: `{ kind, photoIds, text, date, position: { x, y }, size, z }`. Photos are ids from the gallery manifest (`lib/photos.ts`) and are validated server-side against that manifest; no image is copied. Reads and writes go through Route Handlers (`GET`/`POST` on `/api/widgets`, `PATCH`/`DELETE` on `/api/widgets/[id]`) that use a cached Prisma client built with `@prisma/adapter-pg`, which Prisma 7 requires.
- **Context:** The approved schema already carried a JSON `config` column precisely so widget kinds would not need migrations. The gallery is manifest-backed rather than database-backed ([D-015](#d-015--homepage-photo-source-local-manifest-not-the-database)), so there are no `Photo` rows a `WidgetPhoto` link could reference.
- **Consequences:** Adding or renaming a widget setting is an application change only. `WidgetPhoto` remains unused until photos are stored in `Photo`; when that happens, widget photo references should move from `config.photoIds` to that join table, and the manifest validation should become a `photoId` foreign key. The JSON is parsed defensively on read, so a row written by an older build cannot break the page. The widget layout is global — one shared arrangement for the whole application, not per-visitor storage ([D-013](#d-013--single-shared-mimori-with-no-user-or-ownership-model)). Server-side validation rejects unknown kinds, unknown or duplicated photo ids, photo counts outside a style's range, impossible dates and text over 280 characters (`lib/widgets/validate.ts`, covered by unit tests).

## D-026 — The widget canvas: grid positions, a borderless section and drag with motion values

- **Status:** Accepted
- **Date:** 2026-11-02
- **Decision:** Widgets sit at absolute pixel coordinates on a shared canvas and snap to a 16px grid. Positions are clamped to the canvas and an overlapped drop is pushed to the nearest free grid slot, so two widgets never stack by accident. The canvas is **not a panel**: the widgets area is a plain full-width section between the hero carousel and the photo gallery, with no heading, caption, border, background or shadow around it, and the navbar's dynamic **+ Add Widgets** action is its only entry point. There is **no Arrange mode** — every widget is draggable at all times, and its own round options handle (top-right, always rendered, revealed on hover and focus) opens send backward / bring forward / change size / edit / remove. Content is `pointer-events-none`, so a drag can start anywhere on a piece and a photo can never swallow the gesture. The visual drag offset lives in two motion values and is reset to zero when the drop is committed, so dragging never re-renders the tree and the card does not render its offset twice. Sizes follow three presets (small 208×228, medium 288×268, large 384×320), cycled from the options handle; layer order is the stored `z`, with forward/backward swapping neighbours and renumbering the stack.
- **Context:** The brief asked for macOS-style free positioning with snapping, overlap prevention, resize and layer order, on mouse and touch, without drags firing widget interactions. A later refinement asked for the widgets to read as pieces placed directly on the scrapbook page, so the surrounding container, the section heading and the arrange-mode switch were removed.
- **Consequences:** Every widget owns its own controls, so a widget is movable and editable on a phone without a global mode ([ISSUE-014](KNOWN_ISSUES.md) records the one cost: a touch that starts on a widget moves it rather than scrolling the page, because drag needs `touch-action: none`). The empty state is text pointing at the navbar action instead of a button, to keep that action the single entry point. A stray touch can also move a piece, which is intentional — exactly what a desktop-with-widgets behaves like — and a failed write restores the previous position. Positioning is a single global layout in absolute pixels, not per breakpoint: on a narrow screen the CSS `min()` clamp keeps every card inside the canvas and the layout is not saved again, so a desktop arrangement is simply pulled inward rather than rewritten ([ISSUE-013](KNOWN_ISSUES.md)). The canvas measures itself with a `ResizeObserver` plus a `window.resize` listener; because observers can be throttled in embedded or background surfaces, the card styles also use `min()`/`aspect-ratio`, which keeps a widget on-canvas even when the measured width is stale. Every drop writes once, on release. The placement rules (`lib/widgets/layout.ts`) are pure functions with unit tests for clamping, snapping, gap handling and overlap resolution.

The gallery reads `kind = GALLERY` rows newest first; an empty table is the empty state and a failed query is an **error** state — the two are never conflated, and neither produces pictures. The product direction is now that the Gallery is the starting point: an installation with an empty gallery must look deliberately empty, and every image becomes available everywhere only after it is uploaded there. The previous fallback also made an outage look like a populated gallery, which hid database failures.
- **Consequences:** No schema change and no migration: the existing `config` JSON, `CollectionPhoto.photoId`, `Folder.coverPhotoId` and `Widget.config.photoIds` already hold strings, so only their **meaning** changed, together with the validation and read filters. `CollectionPhoto.photoId` still has no foreign key; membership is filtered through the photo table instead, and promoting it to a real foreign key remains a possible later migration. `public/couple-images` stays on disk (it is the couple's own material) but is no longer referenced by any code or page. The very first visit to a fresh installation shows eight colourful carousel squares, placeholder tiles in every picker and the Recently Added empty state; the upload in the Gallery fills them all in, with `GalleryPhotosProvider` refreshing immediately after a successful upload. Widgets keep their photos in `config` rather than `WidgetPhoto`, as before. A slot cannot be emptied again from the UI — it can only be filled with another photo ([ISSUE-019](KNOWN_ISSUES.md)). Validation remains server-side and id-only: a client cannot submit a URL, and unknown ids, unknown slots and blank titles are rejected.

## D-034 — The photobooth is one pure geometry plus a declarative border catalogue

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decision:** The photobooth is a dedicated `/photo-booth` route whose setup step chooses a photo count (2, 3, 4 or 6; default 4), a layout (`strip` or `collage`; default strip) and one of six border templates (`lovely-hearts`, `minimal-white`, `vintage-film`, `flower-garden`, `kawaii-stickers`, `love-letter`; default Lovely Hearts). The counts, layouts and defaults live in `lib/photo-booth/catalog.ts`, the borders in `lib/photo-booth/borders.ts` as data (frame, edge and accent colours, a pattern key, caption plate colours and corner decorations drawn from the shared sticker registry), and the geometry in `lib/photo-booth/compose.ts`. `composeBooth()` is a pure function of that config: it returns the overall composition size, frame and inner page, every photo slot, the optional caption plate and the placed decorations, with slot counts, non-overlap, boundaries and determinism covered by `node:test`. A six-photo strip pairs its frames into two columns; every other strip is a single column. Setup previews are SVG drawn from those same rectangles, so the chosen print is the composition rather than an illustration of it.

Drawing each border as its own component, or measuring the DOM to export, would let the preview and the saved image drift. The project also has a fixed brand palette and no image-composition dependency (`html2canvas`, Fabric, Konva), and none was to be added.
- **Consequences:** The same geometry and template data can drive the camera step, the editor and a canvas renderer, so a border is defined once and no screen hardcodes one; the SVG preview is also the specification for the future export. Border templates store concrete colours and numbers rather than Tailwind classes, which keeps them usable outside React. The setup step is configuration only: nothing is uploaded, persisted or captured, the choices live in `PhotoBooth`'s state, and a reload returns to the defaults; `+ New Photo Booth` links back to the setup anchor rather than resetting that state ([ISSUE-020](KNOWN_ISSUES.md)). The photobooth tables, `Photo.kind = PHOTO_BOOTH` writes and the `PhotoboothSession`/`PhotoboothShot` models remain future work — this phase adds no schema change, migration, API route or dependency, and the Gallery, uploads and widgets are untouched. The `/photo-booth` page is static, so it ships no database read and no client bundle for the title band.

## D-035 — The photobooth captures with the native camera APIs and holds the session in memory

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decision:** Capture uses only browser APIs: `navigator.mediaDevices.getUserMedia()`, a `<video autoPlay muted playsInline>` element, `<canvas>` `drawImage()` and `canvas.toBlob()` — no camera library and no `ImageCapture`, which iOS Safari does not implement. Constraints request the chosen side with `facingMode: { ideal }` at 1280×960, so a single-camera device still opens. The side that actually opened is read from `track.getSettings().facingMode` and drives both the mirrored preview (`scaleX(-1)`) and the mirrored capture, so a front-camera photo matches what the person posed in; the rear camera is never flipped. Frames are drawn at most 1080px wide, never upscaled, and encoded as JPEG at 0.9. The 3-second countdown runs from one deadline with `performance.now()` and is redrawn on an interval; hiding the document stores the remaining time and stops the interval, and returning sets a fresh deadline, so a locked phone never fires a surprise photo. Camera lifecycle lives in `lib/photo-booth/camera.ts` and `components/photo-booth/camera-step.tsx` only: every request stops the previous stream first, tracks are stopped on switch, retry, exit and unmount, and a generation counter plus a running-pass flag make a superseded sequence unable to capture or write. Each shot is `{ id, blob, url, mirrored }` in `PhotoBooth`'s state, with its object URL revoked when replaced, discarded, reset or unmounted. The review step renders those shots through the existing `composeBooth()` geometry rather than a second layout.
- **Context:** Phase 2 asked for a real photobooth camera on desktop and mobile without adding dependencies, while Phase 3 will add a border editor that must change borders without retaking photos. That requires the captured photographs to survive the camera screen as raw images, separate from how a preview renders them, and it forbids rewriting the camera later. The project also has no upload or persistence for photobooth shots yet.
- **Consequences:** No schema change, migration, API route or dependency, and the Gallery's upload path is untouched. Photos exist only in the tab: a reload, closing the tab or **Back to setup** discards them, and nothing is uploaded or saved ([ISSUE-021](KNOWN_ISSUES.md)). Retaking one photo replaces only that slot; retaking all clears the session. A retake pass keeps the session's other photos, so leaving the camera mid-retake returns to the review instead of losing the whole session. Torch is shown only when `getCapabilities().torch` is true and its application can still be refused silently, and real-device behaviour (iOS Safari, Android Chrome, portrait orientation, secure origins) is not verified — the implementation follows the documented APIs but has only run against Chromium's virtual camera ([ISSUE-022](KNOWN_ISSUES.md)). The session state machine has room for an `editor` step between `review` and any save, and the raw Blobs are already kept apart from presentation state for it.

## D-036 — The editor decorates around the captures, and one geometry drives both the preview and the export

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decision:** The photobooth's post-capture editor is a fourth session step whose state is a single `BoothEditorConfig` (`lib/photo-booth/editor.ts`): `borderKey`, `backgroundKey` (null = the template's own paper), sticker placements, caption, date, spacing and frame thickness. Captured photographs are never part of that config — they stay as Blobs and object URLs in `PhotoBooth`, so changing a border, paper, sticker or caption cannot replace, re-encode or revoke a photo. Sticker positions are stored as fractions of the composition (centre x/y, side and rotation), and `composeBooth()` turns them into clamped page rectangles, which is why a sticker keeps its spot and stays on the page when spacing or frame thickness changes the print. The same call now also resolves the paper colour and the caption/date text boxes, and the paper pattern numbers live in `lib/photo-booth/patterns.ts` shared by the SVG previews and the canvas renderer. Both surfaces read the geometry: `components/photo-booth/composition-preview.tsx` for the live print and `lib/photo-booth/client.ts` for the JPEG, which scales the geometry once, draws by those rectangles, awaits Caveat/Roboto, falls back to a paper placeholder for an undecodable photo, and fills the whole rectangle with paper first so the rounded frame's corners do not export black. **Finish editing** renders the JPEG and shows it as the exact export; saving and downloading are not part of this phase.
- **Context:** Phase 1 deliberately kept borders as data and Phase 2 kept the camera's captures separate from presentation so an editor could change borders without another shoot. Repainting the frame, adding stickers, writing a caption and retuning spacing all change the composition's size, so absolute sticker positions would drift and a second layout calculation in the canvas would let the preview and the saved print diverge.
- **Consequences:** No schema change, migration, API route or dependency; the editor is entirely client-side and writes nothing to the Gallery, Cloudinary or the database. A new tab is a new choice group, not a new state store: the five tabs all edit the one config. Caption and date share the caption plate and reserve it whenever either is present; the date printed on the image is formatted from the editor's own `yyyy-mm-dd` value and is unrelated to `Photo.createdAt`. The exported JPEG is 1600px wide and square for the collage layout; the editor preview is a scaled version of the same rectangles, with the same fitted caption size computed by `fitCaptionSize()`. The session still lives only in the tab: a reload, closing the tab or **Back to setup** discards photos and edits ([ISSUE-021](KNOWN_ISSUES.md)). The config has no persistence format yet, so Phase 4 can add one without changing how the editor or the renderer work.

## D-037 — A saved photobooth references photos instead of storing URLs, and saving is uploads plus one write

- **Status:** Accepted
- **Date:** 2026-11-03
- **Decision:** Saving a photobooth adds two tables that reference the existing `Photo` rows and nothing else. `PhotoboothSession` stores the settings as validated columns (`photoCount`, `layout`, `borderKey`, the optional `backgroundKey`, `caption`, `showDate`, `printDate`, `spacing`, `borderWidth`) plus `stickers` as validated JSON, and points at its finished print with `printPhotoId`; `PhotoboothShot` lists the captures with `position`, unique per session, and `photoId` unique across the table so a capture belongs to exactly one session. The print is written as an ordinary `GALLERY` photo and the captures as `PHOTO_BOOTH` photos, which means the Gallery, its pickers, collections and the hero slots find the print through the queries they already use (`kind = GALLERY`) and never see a capture — no gallery code learned about the photobooth. Both kinds go through the existing `/api/photos/upload`, which now accepts an optional `kind` field validated against a closed allowlist (`GALLERY`, `PHOTO_BOOTH`, omitted = `GALLERY`) and picks the Cloudinary folder (`mimori/gallery`, `mimori/photo-booth`); booth captures skip the duplicate check, because a capture must be its own row. The client save (`lib/photo-booth/save.ts`) uploads each capture, then the rendered JPEG, then posts the ids to `POST /api/photo-booth`, which re-reads the rows, checks kinds and count, and writes the session and its shots in one nested create. Every successful upload is cached in memory for retries; nothing is reported saved until that write returns.
- **Context:** Phase 4 had to persist a session whose photos already exist as Blobs and as Cloudinary assets, without a second image store, without duplicating metadata and without weakening the Gallery's `GALLERY`-only filtering ([D-033](DECISIONS.md)). The Phase 3 renderer already produced the exact print, so the only question was where the image and its description live. Storing URLs on the session would duplicate `Photo` metadata and let the two disagree; a separate gallery only for photobooth prints would fork the gallery's queries and pickers.
- **Consequences:** The migration `20261103091753_add_photo_booth_sessions` is additive — two `CREATE TABLE`s, their indexes and three foreign keys, with `ON DELETE CASCADE` from session to shots, from `Photo` to shots, and from the print photo to its session. Deleting a print therefore removes the session that described it; deleting a capture removes that shot. No existing table, row or column was rewritten, and `Photo` gained only relation fields. A session can never describe a different picture than the `Photo` row it points at, and the print behaves exactly like any other uploaded photo — it can be collected, put in a widget or slot, or replaced in the hero carousel. Validation is pure (`lib/photo-booth/session.ts`) and shared by the route, so malformed stickers, impossible dates, out-of-range sliders, duplicate or wrong-kind photos are rejected before any write; `POST` answers 400/409/503 with a sentence, `GET` lists sessions newest first and `GET /api/photo-booth/[id]` returns one session with its ordered captures. Uploads that succeed before a failure are kept for the retry rather than deleted, so a retried save cannot double-upload; the cost is that abandoning a save can leave an unreferenced print in the Gallery and unreferenced captures in Cloudinary ([ISSUE-024](KNOWN_ISSUES.md)). Sessions are still not reopenable: the ids are stored and returned for Phase 5, but nothing loads a saved session back into the editor yet.

## D-038 — A saved booth reopens from its photo references, and an edit replaces only its print

- **Status:** Accepted
- **Date:** 2026-11-04
- **Decision:** A saved session is reopened by reading it, never by copying it. `GET /api/photo-booth/[id]` already returns the settings and the ordered captures; `lib/photo-booth/restore.ts` validates that payload against the same rules the write path uses and rebuilds the editor's `photoCount`, `layout`, `BoothEditorConfig` and shot list. To let one editor serve both visits, `lib/photo-booth/shots.ts` defines a `BoothShot` union: a fresh capture is `{ source: "capture", id, url, blob }` (an object URL that is revoked with the capture), a reopened photo is `{ source: "saved", id: "saved-shot-<photoId>", url, photoId }` (a Cloudinary URL that is never revoked and never re-uploaded). The editor, `CompositionPreview` and the canvas renderer accept either, and the renderer loads a saved URL with `crossOrigin = "anonymous"` so the canvas stays untainted while `toBlob()` exports; a saved photo that fails to load fails the render instead of printing a placeholder. Editing an existing session uploads only a replacement page and calls `PATCH /api/photo-booth/[id]`, whose body carries settings and `printPhotoId` but **not** shots, count or layout: the server reads the captures from the row, refuses any attempt to name photos, re-validates that every capture still exists as `PHOTO_BOOTH`, that the new print is a `GALLERY` photo, is not one of the captures and is not another booth's print, then writes the settings and print together. A reopened editor primes the save cache with the session's own print signature, so saving without a change reuses that row rather than creating a duplicate. After the update commits, the replaced print is deleted with its Cloudinary asset — but only if no other session, collection, widget, hero slot or folder cover references it; otherwise it stays in the Gallery. `lib/photo-booth/summary.ts` merges the returned summary into the library list so a save or update needs no refetch, and **Download print** always renders the current configuration through the canvas renderer, saving `mimori-our-little-moments.jpg`, rather than linking the stored print.
- **Context:** Phase 5 had to make saved booths editable without rebuilding the camera flow, duplicating images or leaving a new Gallery print behind on every edit. The stored captures are Cloudinary images, not Blobs, so the editor needed a photo abstraction that does not care where the pixels come from; and the session's captures belong to the session rather than to one editing pass, so an update endpoint must not accept photo ids at all.
- **Consequences:** No schema change and no migration: `PhotoboothSession.printPhotoId` is simply updated, and the existing cascade rules make a deleted print remove the session that described it. A `PhotoboothShot` is never deleted or rewritten by an edit, so the original frames and their order survive every save. The replacement is ordered so the new print is committed before the old one is considered for deletion, which means a failure at any point leaves the session readable and its previous print intact; the reference check is deliberately conservative (any collection, widget, hero slot or folder cover keeps the old print), and a cleanup failure is logged instead of failing the update. Downloads no longer depend on a previous render, so an unsaved change downloads the composition on screen. The library lists and opens sessions client-side, fetching once and updating from the write responses; opening a booth is read-only. Still unsaved sessions remain tab-only ([ISSUE-021](KNOWN_ISSUES.md)), and abandoned new-session uploads can still be left unreferenced ([ISSUE-024](KNOWN_ISSUES.md)).

## D-041 — Deleting a gallery photo removes the row, its JSON references and its asset, and refuses booth prints

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** Deletion is a server-side `DELETE /api/gallery/[id]` (`lib/gallery-delete.ts`) that takes the photo id in the path and never reads the body, so a client cannot name an asset. It first reads the row and uses **its** `publicId` for the Cloudinary destroy; only a `kind = GALLERY` row is deletable, so booth captures are untouched. A photo that is a saved booth's `printPhotoId` is refused with 409, because that `Photo` cascades to its session and would take the session and its capture links with it. The database goes first in one transaction — delete the photo's `CollectionPhoto` rows, null any `Folder.coverPhotoId` that pointed at it, rewrite every widget `config` that listed it (dropping the hero slot's assignment rather than leaving a dangling reference), then delete the row by id **and kind** — and only then is the Cloudinary asset destroyed. A row that cannot be deleted leaves the asset alone; a destroyed-row with a failed or unreachable `image/destroy` answers `{ deleted: true, warning }` and the UI reports that the file could not be removed instead of a clean success. The viewer applies the confirmed deletion to `GalleryPhotosProvider` (`removePhoto()`), and a saved deletion ends the flow rather than moving inside it: the viewer and its confirmation close together, the photo is already out of the grid (the gallery's empty state takes over when nothing is left), and `PhotoGallery` shows an **Image deleted successfully.** toast that outlives both overlays, so the outcome is announced with no backdrop, overlay or dialog left on the page. The grid, collection pickers, widget photo step and Recently Added all agree without a reload. A failed request leaves the viewer and the confirmation open with the error inside the confirmation and no toast. Collection pages keep the plain viewer: the action exists only on `/gallery`.
- **Context:** Uploads existed but a photo could never leave the Gallery ([D-030](#d-030--the-gallery-is-database-first-with-the-bundled-photos-as-its-fallback-and-uploads-are-server-signed)), and every image reference is now a `Photo` id ([D-033](#d-033--the-gallery-database-is-the-only-image-source-and-the-carousel-has-eight-fixed-slots)). Deleting only the row would have left the Cloudinary asset billing forever and left stale ids in widget and carousel JSON, which have no foreign key; deleting only the references would have kept the picture. `CollectionPhoto.photoId` still has no foreign key, so its rows must be removed explicitly.
- **Consequences:** No schema change and no migration. Nothing is deleted from the database unless the storage integration is configured, because a row removed without its asset could never be cleaned up later from the UI. The hero slot a deleted photo filled becomes **empty** and shows the carousel's existing colourful placeholder; a widget that used the photo keeps its position, size, kind and copy and simply loses that picture (with no photos left it renders its existing "choose photos" state). Deleting is permanent: there is no trash, undo or restore ([ISSUE-027](KNOWN_ISSUES.md)), and a booth print must be deleted by disk/web console or not at all, which is the price of protecting its session. Duplicate submissions are stopped by a ref in the viewer and by the kind-scoped `deleteMany`, whose zero count rolls the transaction back and answers 404. The success message is page-level state, not viewer state, because the viewer must already be gone when it is read; it clears itself after about four seconds and a failed asset destroy shows the warning instead of that success message. The endpoint is not authenticated ([D-013](#d-013--single-shared-mimori-with-no-user-or-ownership-model)), so anyone who can reach the app can delete a gallery photo.

## D-042 — A deletion's confirmation is a page-level pill owned by the widest surviving component

- **Decision:** The outcome of a destructive action is shown as a short pill (`components/scrapbook/status-toast.tsx`: `useStatusToast()` for the message and timer, `StatusToast` for the pill — fixed, centred above the page at `z-[80]`, `role="status"` with `aria-live="polite"`, paper ground, pink heart, ~4.2s auto-dismiss, a new message restarting the timer). The gallery flow already worked this way by request; the collections flow had a worse problem — it closed the confirmation **before** reading the result, so a failure was invisible. Mimori has no toast library and no global notification system, and the two callers need the same look and timing.

Future destructive flows should follow the same pattern: close the dialog, apply the server's response to the shared store, show the pill from the widest surviving component, and never show it optimistically.

## D-043 — One app-wide toast provider replaces the page-level pills

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** Mimori has exactly one toast implementation: `components/toast/toast-provider.tsx`, mounted outermost in `app/layout.tsx`, exposing `useToast().showToast(message, tone)` with `tone` = `success` (paper pill, pink heart) or `error` (danger surface). One message is shown at a time, fixed and centred above every dialog (`z-[90]`), clearing the mobile bottom bar, for about three seconds, animated in and out unless `prefers-reduced-motion`; a new message replaces the visible one, and repeating the same message restarts its timer rather than stacking a second. - **Context:** The gallery's deletion flow and then the collections flow had grown their own pills in two different components, and the request was for every meaningful action — create, update, delete, upload, save — to confirm itself the same way, including after the dialog or the page that raised it is gone. Two copies of the markup and timing, or a third, would have drifted, and neither could be trusted to outlive a navigation.

Because the provider sits above every page and store, a message raised just before `router.push()` (deleting a collection from its own page) is still read on the next page. State is deliberately ephemeral — nothing is persisted, there is no history, inbox or queue, and a message is never the only record of an outcome; the database stays the source of truth. Adding a confirmation is one hook call at the call site that receives the server's result, and never inside a provider or before the response.

## D-046 — The love-story glint is painted per letter, because a clipped gradient never repaints

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** [D-044](#d-044--the-love-story-heading-is-white-with-a-css-only-water-wash)'s mechanism is replaced: the heading no longer clips a moving gradient to its glyphs. `components/our-love-story.tsx` renders **Our Love Story** as twelve `.love-story-letter` spans — the phrase itself once in an `sr-only` span for assistive tech, the letters `aria-hidden` — each carrying its own `animation-delay`, 60ms after the letter before it. `app/globals.css` swings each letter's ink from `--brand-white` to `--love-story-glint` (`#FFC9DF`) and back within the first 18% of a 3200ms loop, so the pooled highlight reaches the last letter about 660ms after the first and then the heading rests white until the next pass. `prefers-reduced-motion: reduce` removes the animation and leaves pure white. The colour requirement in D-044 stands; only its wash is superseded.
- **Context:** The wash shipped, and the heading still looked static. The cause is the property it animated: Chrome caches the paint of text clipped through `background-clip: text` and does not invalidate it when only `background-position` changes, so the animation advanced — the computed position moved from 58.65% to 46.15% in 700ms — while the pixels stayed identical. That was proved by parking the same gradient on solid red and then on solid blue and rendering the identical colour at both ends. Animating the glyph `color` is a paint change the engine always honours, and it animates the letters themselves rather than a layer behind them.
- **Consequences:** One class, one keyframe pair, no JavaScript and no dependency, and the letters never move, so the script type keeps its size, position and the heart behind it. Splitting the words into per-letter `inline-block` spans gives up kerning between adjacent letters; Caveat's shapes are per glyph, so the heading reads as before and occupies the same box in the layout, but a font with cursive joins would need a different technique. The accessibility tree still holds one phrase, because the visible letters are `aria-hidden` and the `sr-only` span carries the text. The cost is twelve small colour animations on one heading instead of one background animation, all of it on the main thread; that is negligible at this size, and it is the price of an effect that is actually visible. The gradient stop `--love-story-glint` lives in the semantic tokens so the tint is not hardcoded in a component.

## D-047 — A collection is read as a photo book whose turning sheet is a chain of bent strips

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** Opening a collection shows its photos in `components/collections/photo-book.tsx` instead of the polaroid grid: two facing paper pages, a spine, a paper stack and soft shadows, with prints mounted through `object-contain` so no image is stretched or cropped. A spread is one sheet — two consecutive photos. The turn is a **sheet that bends**, not a card that swings: the page is cut into twelve strips, laid end to end, each rotated about the edge where it meets the one before it. Strip `i` carries an equal share of the total bend, and the free edge trails the spine edge by up to 38° at the halfway point (zero at both ends). Because each strip starts where the last one ended, the strips form a curved surface in 3D; each carries the sheet's front (the photo being lifted) and back (the page that arrives on the left), so the photo is seen on both sides and the pages underneath are revealed as it sweeps over the spine. The strips are cut in *bend-space* rather than in pixels, so they are wide and nearly flat at the spine and short and tightly bent at the free edge, where a lifted page curls most. Light is derived, not painted: every strip's shade comes from the angle of its own face relative to the room's light, with a sheen where a strip is almost edge-on, and the shadow cast on the page below is sized by where the free edge actually projects and darkens as it narrows into a contact shadow at the spine. The spread is clipped to the book's rectangle: a lifted sheet is magnified by its own depth under perspective, and clipping is what keeps the turned page inside the cover instead of stepping out past it. It is CSS 3D only — no WebGL, no animation library, no page-flip dependency. A turn takes 900ms and eases in and out (a released drag only settles, so it does not restart from rest). Navigation is the two round arrows, ArrowLeft/ArrowRight, and a pointer drag on either half of the book; a tap on a page still opens the existing viewer. The grid stays reachable behind **Manage photos**, so collection CRUD is untouched, and **Close book** returns to `/collections`. Under `prefers-reduced-motion` the turn is skipped and the spread changes at once, and a pointer drag does not start.
- **Context:** The request was for a realistic 3D page turn with perspective, both faces, a revealed page underneath and paper depth — explicitly not a slide, a fade or a flat rotation — while keeping the existing collection data, order and CRUD. A library such as `page-flip` was considered and rejected: it owns page sizing and layout, brings a dependency for one screen, and its sheet model would have had to be reconciled with Mimori's own pages and counter, while the strip technique gives the same geometry on top of ordinary React markup.
- **Consequences:** No dependency, no schema or API change, and the photos stay `Photo` records the book only reads. The sheet is a polyline of twelve planes rather than a continuous shader curl, so the bend is sampled: the angle between neighbours is about three degrees at the peak, small enough to read as a curve, and the shade steps by about 0.013 per strip so the seams are not visible as bands. Twenty-four copies of a page's markup exist (twelve strips × two faces), each a window onto the same page, so only thin strips rasterize and the image is fetched once per URL; that duplication is the cost of not needing a canvas renderer that would itself have to reproduce Mimori's page design. Clipping the spread means a turned page never overhangs the cover, which removes the stepped silhouette the depth magnification would otherwise produce but also loses the small overhang a real page has. Two photos per turn is what a physical sheet does — front and back — so the counter names the right-hand page and an odd collection ends on an empty page with **The end**. On a 390px screen the pages are only about 179px wide, which is why tapping one opens the full viewer. Resizing the window abandons a turn in flight rather than leaving strips measured for the old geometry. The turning sheet is decorative and `aria-hidden`; the readable, focusable pages are the two static ones.

## D-048 — The photo book's turning sheet is a canvas curl with velocity release

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** D-047's twelve-strip CSS 3D sheet is replaced by a single canvas (`components/collections/page-curl-canvas.tsx`): each frame the sheet is sliced into ~70 ribbons sampled from two offscreen page textures (front print + back print) and re-projected along a curl whose free edge trails the spine edge by up to 38° mid-turn, with per-ribbon light, edge-on sheen, a travelling cast shadow and a cut edge. One bitmap means no strip joints, no z-fighting and no seam lines. The drag tracks pointer velocity over a 120ms window: a flick faster than ~0.9 progress-units/s completes the turn even from a short drag, a throw back toward the start cancels a far drag, and otherwise a 22% distance threshold decides; the settle keeps the flick's momentum instead of restarting from rest, so nothing snaps. Still no dependency, no schema or API change, unchanged ordering, counter, arrows, keys, close behaviour and reduced-motion instant jump.
- **Context:** The strip chain could never be a true Apple Books-style curl: it bent only through per-strip `rotateY` steps, kept black joint lines, and a short fast flick was treated as an incomplete drag. A page-flip library was reconsidered and rejected again for the same reason as in D-047 — it would own layout and the sheet model — while the canvas renderer keeps Mimori's pages, counter and textures.
- **Consequences:** The sheet's page design (paper, contained print, caption, page number) is now reproduced in canvas 2D primitives rather than reused DOM, so the two renderings must be kept visually consistent by hand. Texture rebuilds on photo or size change repaint paper immediately and swap photos in on load, so the sheet is never blank. The curl bends only along the horizontal axis with a small vertical skew toward the grab point — a corner grab skews rather than truly curls in two dimensions. Frame cadence and touch dragging were exercised through synthetic pointer events in the desktop browser only; real-device feel is still unverified.

## D-049 — The curl paints the shadow under the sheet and never overlaps its own tones

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** In `components/collections/page-curl-canvas.tsx` the paint order and the rects are rules, not incidental detail. (1) The sheet's geometry is sampled once into `slices` before anything is drawn, so `freeX` — and therefore the cast shadow — is known up front; the shadow is then painted **first** and the ribbons over it, so the shadow can only fall on the page below and never on the paper itself. (2) The shadow's leading edge ramps from zero over a few pixels instead of starting at its full opacity. (3) A translucent per-ribbon tone covers exactly the rect that ribbon's opaque copy filled, so the following ribbon erases the overlap and repaints it — one tone per column, never two (a dark hairline) and never none (a light one). (4) The cut-edge highlight is drawn only when `freeX` is the sheet's outline (`minX`/`maxX`); past edge-on the paper folds back and that highlight would sit across the middle of the face. (5) The opaque image overlap scales with the ribbon's width.
- **Context:** The first canvas curl shipped with a faint grey line across the turning page. It was not a polygon edge or a texture-sampling artefact: the cast shadow was painted after the sheet with its darkest column on the free edge, and the shading rects and the image rects were different sizes, so a column at every ribbon edge was left unshaded. Both are ordering and coverage mistakes, which is why the fix is structural rather than a white overlay or a softer filter.
- **Consequences:** The paper stays one continuous surface at every angle, including the squeezed state near edge-on where ribbons are thinner than a pixel, and the natural centre-spine shading and travelling shadow are untouched — the shadow is measured still present just outside the free edge. The cost is one extra geometry pass over ~70 ribbons per frame (arithmetic only, no canvas calls) and the loss of the per-ribbon sheen gradient in favour of a flat per-ribbon tone, which is invisible at 72 steps. Anything added to the draw later must respect the order: page, then shadow, then sheet, then tones sized to the sheet's own rects.

## D-050 — The mobile header carries the page's action instead of a hamburger

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** `components/nav/site-nav.tsx` renders `PrimaryActionButton` in the header at every width and no longer has a menu toggle, a menu panel, `menuOpen`, its `menuId` or the Escape listener; `MenuIcon` is deleted from `components/nav/nav-icons.tsx` because nothing else used it. Below `lg` the header is the wordmark on the left and that one action on the right; below `sm` the button runs `compact` (13px label, `px-3`, `whitespace-nowrap`) and the plus icon cannot shrink, then returns to the original `px-4` / 14px from `sm`. The desktop bar, its active pill and the fixed bottom navigation are unchanged.
- **Context:** The request was to remove the hamburger from the four main pages while keeping each page's `+ Add …` action visible and functional, with the mobile header still balanced and nothing reachable only through the old panel. The panel held exactly one control — that action — plus a line of helper copy, so removing the toggle without moving the action would have made the action unreachable on mobile.
- **Consequences:** Navigation lives in the bottom bar and creation lives in the header, one control each, so no page lost a flow and the panel's duplicated button is gone (a single mount means one set of focus stops instead of two copies of the same control). The helper sentence that sat under the panel is no longer shown anywhere; it was copy tied to the menu, not to a flow. The label is the only thing that had to give on very narrow screens: at 390px and 360px the original sizing fits, and at 320px the compact sizing keeps "New Photo Booth" on one line with the wordmark beside it (measured: 145.4px button, 11.5px gap, no horizontal overflow) instead of wrapping inside the pill.

## D-051 — The photobooth success screen answers with the saved print, the session and the library

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** Once the server has confirmed a save or update, the finished-print panel offers exactly three actions, stacked full width because the panel's desktop column is 20rem: **Download Print** fetches the session's own stored print (`session.print.src`, CORS-enabled Cloudinary JPEG) and saves it under `PRINT_FILE_NAME` instead of re-rendering the composition; **Keep Editing** clears the rendered preview and the success state and returns to the same editor, whose configuration is still the version that was saved and whose `session` is still set, so the next save is a `PATCH` of that booth; **Go to Photobooth** leaves the editor for the library — `router.push("/photo-booth")` when the booth was reopened on its own route, and the setup step when the booth was saved from the library page — where the list already holds the merged summary. A failed saved-print download reports inline in the same panel rather than failing silently.
- **Context:** The success screen previously offered a download that re-rendered the current composition and a single way back into the editor, so a visitor had no direct path to the print they had just stored or to the booth they had just saved. Rendering again would usually produce the same pixels, but it would also mean the download was a second export rather than the stored page, and it would hide a real defect — a stale or broken stored print — behind a fresh render.
- **Consequences:** What is downloaded is provably the page the Photo Booth holds: the run fetched the same Cloudinary URL the panel shows (200, `image/jpeg`, 821,697 bytes) after an update. The download now needs the CDN to answer, so an offline visitor sees "The saved print could not be downloaded. Try again." instead of a file; the unsaved panel keeps its local render, which is correct there because nothing has been stored yet. Keeping the editor's `session` intact is what prevents a second booth: the checks after **Keep Editing** showed the editor back with its preview and tabs, `/api/photo-booth` still returning two sessions, and the next save a `PATCH` of the same id. Because the actions are `w-full` in a column, they never wrap unevenly (measured 320px at 1280 and 324px at 390, no horizontal overflow). The three labels are title-cased as the request named them, which differs from the sentence case of the pre-save panel's buttons.

## D-052 — The curl's page textures outlive the turn, so a sheet is never shown as blank paper

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** `components/collections/page-curl-canvas.tsx` no longer builds its two page textures from scratch for every turn. (1) Page photos are decoded once per URL into a module-level `pageImages` map with a listener list, and `preloadPageImages()` is exported so callers can warm them. (2) The texture build runs in a `useLayoutEffect`, not a passive effect, so it finishes before the parent's layout effect draws the opening frame of a turn. (3) A texture pair records the sheet it was painted from (`sheetKey`: both photo ids, the face side, both page numbers, the bitmap size); `draw()` refuses to paint when that key does not match the current props, clearing the canvas instead of showing the previous spread's pages. (4) The canvas is mounted for the life of the book and `clear()`ed while idle, so between turns it holds the forward sheet already painted. (5) `repaint()` waits until every photo on the sheet has settled (`ready` or `failed`) before painting, so a photo arriving late completes the same sheet once rather than swapping into a visible one. (6) `photo-book.tsx` preloads the four pages around the current spread and no longer draws from the click handler in `turn()`/`onPointerDown`: the layout effect draws the opening frame, after the sheet's bitmaps match the new props.
- **Context:** The reported fault was a brightness flicker when changing photos. The cause was ordering, not shading: a turn mounted the canvas, the texture effect painted paper, the parent's first frame drew that paper, and the photos then arrived asynchronously and repainted the sheet — so the page under the reader went from photo to bright paper to photo again. The old texture effect also cleared and reallocated its bitmaps on every mount, and the synchronous draw in the click handler could paint the outgoing spread's textures on a backward turn.
- **Consequences:** A forward turn paints no new texture at all (the idle sheet is the sheet that turns); a backward turn rebuilds the pair synchronously from already-decoded photos, before the first frame is drawn, so nothing visible changes. The per-ribbon lighting, sheen, cast shadow and cut edge are untouched — only when and from what the bitmaps are built changed. Memory holds two page bitmaps for the book's lifetime instead of allocating them per turn, and the preloaded photos are fetched as raw CORS URLs, a second request beside each `next/image`-optimised page. A sheet whose photos are still decoding is skipped rather than shown as paper, which can leave one cold turn with no visible sheet if a photo has not arrived yet; the preload runs when the book mounts, so this needs a first turn faster than the first image response.

## D-053 — The heading heart's dash is its measured length, held until the outline is on screen

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** The hand-drawn heart ([D-045](#d-045--page-transitions-live-in-the-layout-as-one-web-animation-and-the-heart-is-drawn-behind-the-heading)) is driven by geometry rather than by normalisation, and starts where it can be seen. (1) `components/scrapbook/heart-outline.tsx` drops `pathLength={1}` and passes the path's real `getTotalLength()` (539 user units) as `--heart-length`; `.heart-draw` sets `stroke-dasharray`/`stroke-dashoffset` from that variable and the `mimori-heart-draw` keyframe runs the offset from the length to 0 over the same 1500ms after the same 220ms pause. (2) The path ends at `126 112`, just past its `124 112` start, so the finished outline closes instead of stopping short at the bottom point. (3) The SVG is `overflow-visible`, so no part of the stroke can be clipped by the viewBox. (4) The component is now a client component: if the heart is off screen it holds the drawing at its first frame and plays it on `IntersectionObserver` entry, and it re-checks once 600ms after mount, because the widget area's data arrives after the first paint and moves **Our Love Story** out of the viewport. `prefers-reduced-motion` returns before any observer is created and the CSS shows the finished heart.
- **Context:** The four headings' hearts visibly stopped short of their outline. Two causes, both structural: a dash of `1` relied on `pathLength` scaling CSS dash arrays, which is not applied consistently (a one-unit sliver in Safari rather than the whole path), and the path's own last point sat 10 units from its first, leaving a deliberate-looking gap exactly where a viewer reads the end of a drawing. A third problem was placement in time: **Our Love Story** is below the fold on every width, so its heart had finished before anyone scrolled to it. A server-component, no-JavaScript animation was the right default until the heart needed to know whether it was visible.
- **Consequences:** The dash now matches the geometry in every engine, and the finished heart is provably complete (`stroke-dashoffset: 0` with a dash equal to the path's length). The cost is a magic number beside the path: `HEART_FRAME_LENGTH` must be re-measured if `HEART_FRAME_PATH` changes, which the comment says. Four small client components now hydrate on pages that are otherwise server-rendered, and each holds one `IntersectionObserver` until its heading enters, then disconnects. The 600ms re-check exists only for post-paint layout shifts; a heading that moves below the fold later than that keeps the old behaviour of finishing unseen rather than being replayed. Page-to-page navigation is unchanged — a route's own heart is a new mount, so it draws again.

## D-054 — Mimori is an installable PWA that caches only static assets and never personal data

- **Status:** Accepted
- **Date:** 2026-11-08
- **Decision:** The app ships as a PWA using Next.js's native metadata routes and a hand-written service worker, with no third-party PWA package. `app/manifest.ts` serves `/manifest.webmanifest` (standalone, `orientation: any`, `start_url: /`, background `#FF69B4`, theme `#FF4FA3`) with 192/512 `any` and maskable icons from `public/icons/`; `app/layout.tsx` adds the Apple touch icon and `viewportFit: cover` for safe-area insets. `public/sw.js` is registered by `components/pwa/service-worker-register.tsx` and caches only GET requests for `/_next/static/`, `/icons/`, the manifest and a precached `/offline` page. Navigations are network-first and never written to the cache; every `/api/*` route, every cross-origin request (Cloudinary included) and every non-GET method passes straight through. `components/pwa/install-prompt.tsx` shows the native install button when `beforeinstallprompt` fires, shows Share → Add to Home Screen steps on iOS Safari (which has no such event), hides itself in standalone mode or after `appinstalled`, and remembers a dismissal in `localStorage`.
- **Context:** Mimori's gallery, collections and photo booth hold personal, frequently changing data, and the photo booth uploads through the API. A cache-everything strategy would serve deleted or stale photos and could cache upload responses, so the worker is deliberately limited to content-hashed bundles and icons. Safari has no install prompt API, so iOS is handled with instructions rather than a button.
- **Consequences:** Offline, the user sees the friendly offline page for any navigation rather than stale data, and nothing that needs the network pretends to work offline. The install prompt is a single non-modal bar that does not reappear after a dismissal. The service worker updates on the next visit (`skipWaiting` is not called), so an update never reloads a page mid-interaction. Because only static assets are cached, the offline experience is limited to the fallback page. Verified on the production build (see [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md)); the Windows, macOS, Linux, ChromeOS, Samsung Internet and iOS installation paths were not exercised on real devices.

## D-055 — The mobile bottom bar's frame is pointer-transparent, and content clears the bar plus the home-indicator inset

- **Status:** accepted
- **Date:** 2026-11-09
- **Decision:** The mobile bottom bar is one `fixed` element pinned to the bottom edge above the page (`z-50`), whose container is `pointer-events-none` with the visible pill set back to `pointer-events-auto`. The content column reserves `calc(6rem + env(safe-area-inset-bottom))` at the bottom, and the bar itself is lifted from the edge by `max(0.75rem, env(safe-area-inset-bottom))`.
- **Context:** A fixed bar that looks like a floating pill still occupies a full-width rectangle: the transparent strip beneath it and the pixels beside its rounded corners were intercepting taps meant for the content there, which read as "the nav is on top of my button" even though nothing was visibly covered. Separately, the bar is lifted by the safe-area inset on a phone with a home indicator, so a flat `6rem` reserve left 34px less room on exactly the devices with the least.
- **Consequences:** Everything the bar visually covers is the bar; everything it does not cover stays tappable, matching a native tab bar's empty edges. The reserve tracks the inset automatically, so the gap between the last content and the bar is the same on an iPhone and on a flat-edged phone without per-device branches, and the page never needs a per-route bottom padding for this. The bar remains a floating pill rather than a full-width sheet, so the strip below it shows the page background, and the app's other floating controls (toast, collection FAB, selection bar) keep their own offsets above it.

## D-056 — The mobile experience is fixed-scale: no pinch, no double-tap zoom

- **Status:** accepted
- **Date:** 2026-11-09
- **Decision:** The viewport emits `width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no`, `html` sets `touch-action: pan-x pan-y`, and Safari's own `gesturestart`/`gesturechange` events are cancelled by a small client guard (`components/pwa/zoom-guard.tsx`). Nothing else changes: scrolling, the scroll-snap carousels, the photo book's page drag, widget and sticker dragging and every other single-finger interaction keep the `touch-action` they already had.
- **Context:** Mimori is an installable PWA and was being zoomed by accident during ordinary touch use — a second finger while pinching a print, or a quick double tap, left the interface at a different scale with the bottom bar and dialogs out of proportion. A native app does not zoom its own chrome.
- **Consequences:** Pinch and double-tap no longer change the scale, so the app keeps the layout it was designed with. `pan-x pan-y` is deliberately the most permissive value that still excludes zoom: panning stays available in both axes, which is what vertical scrolling and the horizontal carousels need, and a component can still narrow it (`none` for a drag surface, `pan-y` for the photo book). Browsers that ignore `userScalable` are covered by the CSS, and iOS — which ignores `user-scalable` — by the pinch guard, so no global `touchmove` blocker is needed. The cost is accessibility: WCAG 1.4.4 expects content to be zoomable to 200%, and page pinch is now refused on purpose ([ISSUE-030](KNOWN_ISSUES.md)); the browser's own text-size setting and the operating system's magnifier still work.

## D-057 — Every dialog enters and leaves through one shared motion definition

- **Status:** accepted
- **Date:** 2026-11-09
- **Decision:** All dialogs — the collection form, confirmations, the gallery viewer, the upload dialog, the hero picker, the widget dialog and the photobooth sheet — read their overlay and panel motion from `lib/modal-motion.ts` (`useModalMotion(kind)`), wrapped in `AnimatePresence` by whoever mounts them. Two kinds: `sheet` (bottom sheets that rise from below the viewport edge on a phone and lift 28px on desktop) and `center` (cards that are centred at every width and rise a smaller distance). Opening runs 340ms on `[0.16, 1, 0.3, 1]` (out-expo) fading in as it moves; closing runs 240ms on `[0.4, 0, 1, 1]`, dropping 18–40px while it fades. Reduced motion removes travel and duration entirely. The page scroll lock moved into the same module as a counter, so overlapping dialogs release it exactly once.
- **Context:** Dialogs had accumulated three different hand-written animations — a 160ms overlay fade with a `scale(0.98)` pop in the viewer, a `scale(0.95)` pop in the widget dialog, nothing at all in the collection dialogs — and each one was only present while its state was open, so closing was a hard cut. They also each saved and restored `body.overflow` themselves, which leaked: a dialog still playing its exit restored the locked value while a second dialog was already open behind it.
- **Consequences:** A dialog now behaves the same everywhere and cannot drift: changing the easing or the travel is one edit, and a new dialog gets the behaviour by using `ModalShell` or spreading the hook rather than copying keyframes. Because the exit is real, the component must stay mounted for it — every owner wraps the dialog in `AnimatePresence`, and a dialog that only animates while open would silently lose its close animation. The `center` kind is used for the photo viewer so a desktop card does not slide across the whole screen, and `sheet` for everything that is a bottom sheet on a phone. `lockBodyScroll()` also compensates the removed scrollbar with `padding-right`, so opening a dialog does not widen the page by the scrollbar's width on platforms with classic scrollbars.
